# ゲーム内コントローラ登録とEscメニュー

2026-10-15の決定。複数PCへ同じUnityビルドを配り、全ESPにはこのMacから同じファームウェアを書き込む。接続先PCとP1/P2はゲーム画面で登録し、書き込み元のMacやUSB接続順では決めない。

## 今回の変更範囲と実装状況

Esc画面、実機の登録・保存・再探索、スマホの軸調整を実装した。書き込み入口は `make controller`、Unity用PlatformIO環境は `unity_controller` の1種類。元からあったセンサー実験用 `gyro_test` / `gyro_test2` は維持する。

全ESPに同じファームウェアを書き込み、ゲーム内でPCとP1/P2を登録する。未登録の実機は操作データを送らず、登録後は対象PCへのユニキャストだけを行う。PCごとのIP固定や、P1/P2別の再書き込みは不要。旧ファームウェアの裸のKJパケットは新しいUnityハブでは採用しないため、UnityとESPを一緒に更新する。

## Escメニューの導線

Escで開く画面では、中央に大きなQRコードを常時表示しない。横の設定欄に次の3項目を置く。

1. タイトルに戻る
2. やり直す
3. コントローラ

「タイトルに戻る」は進行中のゲームを終了してタイトルへ戻す。「やり直す」は現在のモードを最初から開始する。これらでコントローラ登録は消さない。Escでメニューを閉じると元の画面を再開する。登録・軸調整中もゲームは停止し、受信処理だけを継続する。

登録の画面遷移は次のとおり。

```text
Escメニュー
  → コントローラ
  → P1 / P2を選ぶ
  → 選んだプレイヤーの登録待ち
       QRを読み込む、または
       実機のガード＋リセットを1秒間同時押し
       ├ 実機：割り当ての確定応答を受けたら登録完了 → Escメニュー
       └ スマホ：DataChannel接続 → 軸調整
                    → 6通りから軸の組み合わせを選ぶ
                    → X/Y/Zそれぞれ正転・反転を選ぶ
                    → 確定 → Escメニュー
```

QRは登録待ちの画面にだけ、選んだP1またはP2の分を表示する。QRの読み取りやWebページの表示だけでは接続完了としない。スマホ側で必要なセンサー許可を得て、対応するDataChannelが接続したら軸調整へ進む。実機は軸調整へ進めず、そのままEscメニューへ戻す。

登録待ち・軸調整からのEsc／戻るは直前の画面へ戻る。登録待ちの終了時には募集を閉じ、遅れて届いた登録要求や古いQR接続で割り当てを変更しない。新しい登録が確定するまでは元の割り当てを保持する。同じ枠にスマホと実機が同時に到着したら、最初に受理した一方で今回の登録を進める。

## スマホの軸調整

軸の組み合わせは出力X/Y/Zに対応する入力軸の順番として、次の6通りを選択する。

| 選択肢 | 出力X | 出力Y | 出力Z |
| --- | --- | --- | --- |
| XYZ | X | Y | Z |
| XZY | X | Z | Y |
| YXZ | Y | X | Z |
| YZX | Y | Z | X |
| ZXY | Z | X | Y |
| ZYX | Z | Y | X |

順番を選んだ後、出力X/Y/Zの各軸について「正転（そのまま）／反転」を個別に選ぶ。ユーザー指定の「順点」は「正転」として扱う。順番6通りと符号8通りを別々に選び、48個のプリセットを一度に並べない。

調整中は実際の剣の動きと上下左右を確認できるようにする。スマホの固有IDはブラウザに保存し、ゲームはプレイヤーごとに登録したIDを保存する。軸調整はそのスマホのブラウザにP1/P2別で保存し、他のプレイヤーや実機の軸へ適用しない。調整中は仮適用し、完了でブラウザから保存応答を受けてからEscへ戻る。キャンセルは元の軸設定へ戻す。設定応答には次の送信連番を含め、古い設定の遅延パケットを捨てる。確定時に正面基準と動作履歴を更新し、設定変更で生じた姿勢差を攻撃・メニュー移動にしない。

姿勢、角速度などの変換は同じ軸設定を参照する。quaternionの成分を単純に並べ替える実装にはしない。メニューと戦闘は調整後の共通の剣姿勢を使い、メニュー専用の別補正を追加しない。

## 実機の登録とUDP通信

ESPとゲームPCは同じLANに接続する。Wi-FiのSSID・パスワードだけは共通ファームウェアのビルド時に設定する。PCごとのIP、P1/P2、LED色はファームウェアへ固定しない。ルーターでのDHCP予約は必須にしない。

1. ゲームでP1/P2を選ぶと、そのPCが選んだ枠の登録待ちになる。
2. ESPのガード（GPIO1）とリセット（GPIO0）を連続1秒間同時押しすると、固有のdevice IDと今回の要求IDを含む登録要求をブロードキャストする。
3. 登録待ちのPCだけが要求に返答する。返答にはPCを識別する永続host ID、対象slot、今回の募集IDを含める。IPは返答元アドレスから取得する。
4. ESPとPCが登録確定とその応答を交換する。双方で完了したらPC・ESPに保存し、ゲームはEscメニューへ戻る。UDPの損失を考慮して再試行し、重複要求は同じ登録として扱う。
5. 通常の姿勢・ボタンデータは、登録したPCのIPへUDPユニキャストで送る。PCからの接続確認・振動も直接返す。操作データを常時ブロードキャストしない。

UDP自体は接続確立・到達保証・再送を提供しない。ここでの登録・確定・再試行はアプリ側の処理である。操作データは最新値を使い、古い姿勢を再送して待ち行列を作らない。既存の100Hz目標、CRC・連番・タイムアウトによる検証を維持する。

登録用メッセージと操作データを明確に区別し、操作パケットを受け取っただけで登録しない。登録要求は48-byte KP v1、操作データは88-byte KD v1（内側は64-byte KJ v1）、振動応答は40-byte KD v1（内側は16-byte KA v1）を使う。PCはUDP42042、ESPは42043を使う。正確な形式は `apps/kojo_HW/docs/PROTOCOL.md` に記録する。device IDと登録セッションを照合する。送信元IPだけを永続的な個体IDとして扱わない。

同時押しは1回の押下につき登録要求を1回開始し、再度開始するには両ボタンを離す。登録操作中は通常のガード決定・リセット短押し・リセット単独長押しを発火させない。特に既存のリセット長押し判定が1秒より先に動いて登録画面を閉じないよう、同時押しの判定を優先する。

## 混線防止と再接続

- 初期運用では登録操作をPC1台ずつ行う。最初の候補を受けてから1秒間に複数PCから候補が返った場合、ESPは最初の返答を無条件採用せず登録を中止し、ゲーム側から再試行できるようにする。通常通信中のPCは新しい登録要求へ応答しない。
- 1個の実機を同じPCのP1とP2へ二重登録しない。別枠へ付け替えたら古い枠の実機割り当てを解除する。他PCへ付け替えた場合も旧セッションの入力・振動を受理しない。
- ESPはhost IDと割り当て、PCはdevice IDと割り当てを `~/.kosen-chanbara/controller-pairing.json` に保存する。電源を入れ直しても再書き込みは不要とする。台ごとのLED色を用いる場合も登録応答で渡して保存する。
- IPが変わって通信できない場合は、保存したhost IDを指定した探索だけを低頻度でブロードキャストする。登録済みの相手を確認できたらIPを更新して直接送信へ戻る。他PCへ自動で乗り換えない。接続応答が1.2秒途切れたら2秒間隔で探索する。登録要求・確定要求は400ms間隔で再試行し、10秒で打ち切る。ゲーム側の候補は12秒で期限切れになる。
- 受信は登録済みdeviceと現在のセッションに限定する。古い応答、別の募集ID、別のdevice宛ての応答は破棄する。CRCは認証ではないため、セッション照合と混同しない。
- LAN内の端末間通信とUDP受信を許可する。PCは同じLANへの有線接続でもよい。
- スマホは既存のWebRTC経路を維持する。プレイヤーごとのスマホ接続中優先、未接続時の実機への復帰、キーボード併用は維持する。

## 共通ファームウェアの書き込み

`.env` に最大3組のWi-Fi設定を登録する。例えば `WIFI_SSID1` / `WIFI_PASS1`、`WIFI_SSID2` / `WIFI_PASS2`、`WIFI_SSID3` / `WIFI_PASS3` とする。`WIFI_SSID_1` のように番号の前へ `_` を入れる形式も使える。番号なしの `WIFI_SSID` / `WIFI_PASS` は1番として扱う。

```sh
just controller 1
just controller 2
just controller 3
PORT=/dev/cu.usbmodem... just controller 2
python3 scripts/controller_test.py build 2
```

番号は書き込むWi-Fi設定を選ぶ。ESPは1台ずつつなぐか `PORT` で対象を指定する。本番用のP1/P2別・PC別PlatformIO環境は設けない。元からあった `gyro_test` / `gyro_test2` はセンサー実験用として残す。Unity用の `unity_controller_test_p1` / `unity_controller_test_p2` / `unity_controller_uart` も共通の `unity_controller` に統一する。スマホの起動・停止は従来どおり `just phone-start` / `just phone-stop`。

Wi-Fi設定やファームウェア自体を変更する場合は再書き込みする。PCやP1/P2の変更はゲーム内の再登録で済ませる。

## スマホサーバーとビルド配布

`just phone-start` はEditor用StreamingAssetsと、ビルド版が優先して読む `~/.kosen-chanbara/controller-connection.json` の両方へ接続設定を同期する。起動済みサーバーを再利用する場合も同期する。ゲームは起動中に変更を再読込する。

同じMac上のスマホサーバーを複数PCから利用する場合、`ws://127.0.0.1:8080/signal` はそのPC自身を指すので、全PCから到達できるMacのLANアドレスを指定する。例えば `UNITY_SIGNALING_URL="ws://<MacのLAN IPv4>:8080/signal" just phone-start` として設定を生成し、その設定を含めてビルドするか、各ゲームPCの `~/.kosen-chanbara/controller-connection.json` へ配る。シグナリングサーバーはPCごとに別のセッションを作る。ESPの登録情報ファイルはPC間で共有しない。

Macで起動したゲームの実機入力はスマホサーバーを経由しない。スマホを使わない台にはNode.jsやスマホサーバーの起動は不要。

## 確認項目

- 同一バイナリを入れた複数の実機を、別々のPCのP1/P2へ登録できる。
- 登録完了後は該当PC・該当プレイヤーだけを操作し、通常姿勢データはユニキャストになる。
- 実機の登録成功でEscへ戻り、スマホでは軸順序6通りと各軸の正転・反転を選んでからEscへ戻る。
- 複数PCの登録待ち、2本同時の要求、登録要求・確定応答の欠落や重複、途中キャンセルで誤登録しない。
- 電源再投入・Unity再起動・PCのIP変更で、保存した相手への再接続を確認する。
- 同時押しがガード決定・リセンター・Esc開閉を起こさず、登録後のボタン解放でも誤操作しない。
- 調整後のスマホ入力をゲーム・メニューで共用し、P1/P2や実機へ設定が漏れない。
- Unity Editorだけでなく、複数PCに配ったビルドでも登録・保存・復帰を確認する。
